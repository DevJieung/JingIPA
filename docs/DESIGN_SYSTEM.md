# 올인 디펜스 디자인 기준

이 문서는 `graphic_design_manager`가 세션 사이에 이어 읽는 디자인 기준이다.
최신 사용자 지시와 현재 사용 중인 코드·에셋을 우선한다. 변경 시 근거 파일도 함께 갱신한다.
역할 정의: [graphic_design_manager](../.codex/agents/graphic_design_manager.toml).
분담 규칙: [AGENTS.md](../AGENTS.md).

## 현재 기준

- 앱을 켰을 때는 `docs/icon-business-v3-512.png` 원본을 중앙에서 페이드 인·아웃한다.
  로고 바탕과 화면 전체 여백은 정확히 `#235D48`(RGB 35, 93, 72)이며 엔진 기본
  Godot 아이콘과 Android 시작 아이콘은 표시하지 않는다. 구현: `game/startup_splash.gd`,
  `project.godot`, `export_presets.cfg`, `art/ui/startup_blank.xml`.
- Godot 2D 픽셀아트 게임이며 Android 가로 화면을 대상으로 한다. 기준 뷰포트는
  1280×800이고 작은 화면 검수는 1000×625로 한다. 근거: `project.godot`.
- 현재 팔레트·카드·희귀도 표시는 `core/look.gd`, 공통 UI는 `core/ui.gd`를 기준으로 한다.
  어두운 배경, 밝은 본문, 금색 강조와 현재 야영지 소재의 일관성을 유지한다.
  카드의 픽셀 격자는 `Look.PX`를 따른다.
- 캐릭터 카드의 배경·테두리는 속성 기준이다: 물은 파랑, 불은 주황, 얼음은 하늘색,
  전기는 노랑, 무상성은 은회색이다. `Look.hero_card_face/edge/panel`을 공유하며
  등급은 별, 선택은 흰 외곽선·체크 표식, 새 영웅은 별도의 NEW/방금 뽑은 카드 표기로 구분한다. 이 상태들이 속성색을 바꾸지 않는다.
- 영웅 카드는 원화·이름·속성·별과 선택/신규 표시만 담고 역할·사거리·전투 수치는
  표시하지 않는다. 전투 수치는 `영웅 정보` 탭의 상세 모달에서만 표시한다. 대기실과
  뽑기 뒤 편성의 합성 탭명은 모두 `영웅 합성 / Hero Fusion`이다.
  영웅 정보의 전장 목록은 작은 원화의 가로 카드 6열×2행이며, 전장의 영문 빈칸은
  `Empty` / `slot` 두 줄이다. 근거: 2026-09-21 `voc1.jpg`~`voc3.jpg`,
  `game/hero_card.gd`, `hero_view.gd`, `draw_screen.gd`, `shop_screen.gd`.
- 전장 배치의 전당 속성 필터는 속성 이름 없이 아이콘과 영웅 수만 두 행으로 표시한다.
  영웅 정보의 목록 제목은 `전장에 배치된 영웅` / `전당에 대기중인 영웅`이며 인원·자리·
  페이지 수와 우측 터치/드래그 설명은 표시하지 않는다. 영웅 정보의 정렬 버튼과 터치
  영역은 제거하고 기존 전당 순서와 스크롤을 유지한다. 두 머리글 아래 카드까지는 기존보다
  12px씩 여백을 더 둔다. 근거: 2026-09-21 후속 사용자 요청,
  `game/formation_view.gd`, `game/hero_view.gd`.
- 게임 종료 광고의 최고등급 영웅은 전당에 보관하고 별도 획득 화면에서 이름·등급·원화,
  전당 보관 위치와 크리스탈 전체 회복을 명확히 알린다. 금빛 광선·입자·고리 연출 뒤에도
  확인 전까지 화면을 유지하며 `영웅 배치 / Arrange heroes`를 누르면 편성으로 이동한다.
  `last_result.reward_pending`을 저장해 재접속 시 미확인 획득을 다시 보여 주되 재지급하지
  않는다. 연출: `game/revive_reward_view.gd`; 지급/확인: `Run.revive_wave/acknowledge_revive_reward`.
- 광고 부활은 같은 판·같은 탄에서도 횟수 제한 없이 반복할 수 있다. 패배 화면은 이전
  부활 여부와 무관하게 동일한 광고 버튼·보상 안내를 표시하며 기회 소진 문구를 두지 않는다.
  근거: 2026-09-22 사용자 요청, `game/over_screen.gd`, `Run.reward_allowed/revive_wave`.
- 공통 글꼴은 번들 `core/fonts/RefugeSans-Bold.otf`다. 작은 한국어·영문·숫자도 실제로
  읽혀야 한다. 카드 무늬는 기존 `Look.draw_suit()` 표현을 재사용한다.
- 타이틀은 번들 글꼴의 한국어 `올인 디펜스` / 영어 `All-in Defense`를 금색 금속 전면,
  청동 입체면과 얇은 테두리로 그린다. 위에는 세 장의 카드·스페이드 방패 문장,
  아래에는 반대 언어의 작은 브랜드명과 얇은 금색 장식을 둔다. 도감 모달이 열리면
  워드아트 캔버스를 숨긴다. 근거: `game/title_screen.gd`, `art/ui/title_wordmark.gdshader`.
- 상점의 능력치 현재값·다음값·최종값은 백분율 없이 `x1.20` 형식으로 통일한다.
  치명타 확률은 실제 확률 계수(`x0.05`), 몬스터 이동속도는 이동속도 계수(`x0.95`)이며
  무료 교체는 횟수 단위를 유지한다. 패시브도 능력치 변화는 x로 쓰되 가산 효과는
  `x0.10 추가`처럼 명시한다. 발동 확률·체력 임계값은 강화 배수가 아니므로 보존한다.
  근거: 2026-09-16 사용자 요청, `core/balance.gd`, `game/shop_screen.gd`.
- 카드 교체는 `무료 잔여 / Free left`와 횟수를 별도 상태 칸에, `교체 / Redraw`를
  그 아래 조작 버튼에 표시한다. 무료가 소진되면 상태 칸을 `교체 비용 / Cost`와 G로
  전환한다. 능력치의 무료 교체 현재·다음은 활성 큰손 패시브까지 포함하며, 현재값은
  포커 화면 카드당 초기 횟수와 같아야 한다. 근거: `Run.free_rerolls_at/rerolls_left`,
  `game/draw_screen.gd`, `game/shop_screen.gd`와 2026-09-20 후속 사용자 요청.
- 광고 카드 교체창은 네 무늬 × 13장 전체를 한 화면에 표시한다. 무늬 탭이나 페이지로
  후보를 숨기지 않는다. 현재 손패/족보와 교체 후 손패/족보를 함께 보여 준다.
  52장 목록의 현재 교체 대상은 카드 뒷면으로, 나머지 보유 4장은 `보유 중 / In hand`
  리본으로 구별한다. 근거: 2026-09-15~16 사용자 요청, `game/card_choice_view.gd`.
- 합성 재료는 동일 캐릭터 보유분을 개별 카드로 전부 표시하고 같은 캐릭터끼리 연속
  배치한다. 출전 카드는 목록에서 완전히 제외하며 별 오름차순, 속성 순으로 정렬한다.
  대기 보유분의 각 슬롯을 따로 선택하며 `Run.fusion_material_allowed()` 판정을 공유한다.
- 합성 결과를 받기 전에는 성공·최고 등급을 포함해 항상 `재료 되돌리기` 광고 버튼을 표시하고, 재합성마다 새 광고를 완료하면 다시 원복할 수 있다. 근거: 2026-09-21 사용자 요청, `game/fusion_view.gd`, `core/run.gd`.
- 상단 우측 16px 안전 여백에는 공통 `KOR`·`ENG` 두 선택 버튼을 항상 둔다. `메뉴 / 도움말`은
  그 왼쪽, 전투 배속과 다음 탄 정보는 메뉴 왼쪽에 둔다. 모달에서도 언어 전환이 가능하다.
  근거: `Hud.MENU_RECT`, `Hud.LANGUAGE_RECT`, `game/menu_overlay.gd`.
- 메뉴의 `속성 상성표`는 캐릭터 속성 5개를 세로, 몬스터 몸 속성 5개를 가로로 두고
  25칸 전체에 `Balance.elem_mult()`의 2배·1배·0.5배·0배를 표시한다. 아이콘과 이름,
  축 화살표, 숫자와 범례를 함께 써 색만으로 상성을 전달하지 않는다. 이전 아이콘
  목록을 대체한 2026-09-16 사용자 요청이며 구현은 `game/menu_overlay.gd`다.
- 캐릭터 미리보기는 `Art.unit_preview()`가 읽는 `art/portraits/<id>.png`를 우선한다.
  전투용 작은 프레임을 상세창에서 무리하게 확대하지 않는다. 전용 원화가 없을 때의
  대기 프레임·정지 그림 대체 동작도 유지한다.
- 전투·UI 텍스처의 Nearest 기본값과 초상화의 개별 필터 처리를 구분한다.
  얼굴·팔다리·무기, 긴 소개문, 정보와 버튼이 각각 자기 영역 안에 보여야 한다.
- 애니메이션의 현재 규격은 실제 `art/anim/` 시트와 `anim.json`, `core/anim.gd` 및
  참조 데이터로 확인한다. 과거 문서의 96×96을 모든 시트에 강제하지 않는다.
  기본 배우 프레임은 256×256이며 넓은 무기는 투명 캔버스를 확장하고 실제 발 좌표와
  스케일을 보존한다. Shot은 128×128이다.
- 같은 캐릭터의 대기·공격에서 발 원점, 체격, 팔레트가 안정적이어야 한다.
  공격 프레임·총구·투사체와 전투 타이밍의 계약은 메인 에이전트와 함께 검증한다.
- 희귀도·속성·버튼 상태는 색 이외의 기존 별·아이콘·텍스트 표현도 활용한다.
  최신 화면에서 의도적으로 제거한 안내 문구를 예전 문서만 보고 복원하지 않는다.

## 작업별 기록

디자인을 실제로 바꾼 작업에서만 아래 내용을 짧게 남기거나 관련 문서를 링크한다.

- 사용자 요구와 확정된 스타일·가독성 결정
- 사용 원본·수정 에셋·관련 시각 코드의 경로
- 실제 화면 또는 애니메이션 미리보기와 검증 결과
- 다음 작업에서 이어서 처리할 미해결 사항

이번 전담 역할 설정은 기존 디자인을 변경하지 않는다. 현재 기준은 위 파일을 읽고
정리한 것이며, 이 문서 작성만으로 새 화면·스프라이트 검증을 수행한 것은 아니다.

## 2026-09-14 속성별 광역 영웅 스프라이트

- 물 `thalassa`, 불 `brasa`, 얼음 `sigrid`, 전기 `lugh`, 무속성 `blank`를 선정했다.
  모두 현재 로스터의 `role=area`, `bullet=zone` 영웅이다. 몬스터 몸 속성인 나무·바위는
  플레이어 영웅 속성에 포함하지 않는다. 새 영웅이나 전투 수치 변경은 없다.
- 기존 원화의 호스·보일러 방열판·냉각팬·발전기·백색 방벽 장비를 유지한다.
  새 전투 시트는 `art/anim/<id>/<id>_aoe_v1_{idle,attack,shot}.png`이며 해당
  `anim.json`의 현재 `name`으로 로드한다. 배우는 256×256, Idle 8칸 / Attack 12칸,
  Shot은 128×128 4칸이다. 생성한 4개 자세를 원래 프레임 시간에 맞춰 배열했다.
- 실제 알파는 0/255다. 원본의 RGB 체크무늬 결과는 폐기본으로 보관하고, 단색 키 배경을
  내장 image_gen으로 생성한 후 매팅·Nearest 축소·공유 팔레트·발 고정으로 정리했다.
  생성 이미지의 칸 간격을 맹신하지 않고 빈 경계를 찾아 추출한다. 루흐의 긴 번개는
  image_gen으로 길이를 수정해 다음 칸 침범을 해소했다.
- 원래 `hit_ms`, `anchor`, `scale`, `muzzle_at`은 보존한다. Shot은 대상 위치에서
  `AreaFx.zone(..., shot)`으로 재생하며 기존 예고 시간·반경·피해 틱을 따른다.
  충전→확장→폭발은 같은 크기 기준과 바닥 원점을 사용하고 마지막 조각은 중앙으로 흩어진다.
- 제작 원본·이전 승인 시트·전체 프롬프트: `art/animation/element_aoe_v1/manifest.json`,
  `source/`, `previous/`. 재현 도구는 `tools/sprite/element_aoe.py`다.
- 실제 Godot 1280×800 / 1000×625에서 12프레임 합본과 14프레임 전투 연출을 직접
  검수했다. 기준선·장비·글자·전투 레이어와 충전/방출/복귀를 확인했다. 자료:
  `build/element-aoe-sprites/<해상도>/showcase.png`, `battle_08.png`,
  `godot_attack_sequence.png`, `element_aoe_playback.gif`.
  `qc_game.py --only thalassa,brasa,sigrid,lugh,blank` 5명 전원 통과: 발 흔들림 0px,
  테두리 접촉 0px, 유효 알파·팔레트·해시·메타데이터 일치. Android 기기 육안 검수는 별도다.


## 2026-09-14 전체 영웅 50명 스타일 적용

- 사용자가 승인한 광역 5명을 그대로 두고 남은 기존 45명에 새 Idle 8칸 / Attack 12칸 /
  Shot 4칸을 적용했다. 새 소스는 `imagegen_roster_v1`, 현재 로드 prefix는
  `<id>_roster_v1`이다. 근거: `art/animation/roster_v1/manifest.json`, `README.md`.
- 기존 전용 초상화의 얼굴·머리·체형·복장·장비를 유지하며 총/활/검/호스·사슬/광역 장비별
  공격을 구분한다. 이동탄은 작고 우향으로 반복하며, 빔과 고유 연쇄는 가늘게 연결하고,
  장판은 실제 원형 범위에서 충전·확장·폭발·소멸한다. 고유 연쇄의 시각 출처 `shot_src`와
  패시브 번개를 구분하며 `Fx.clip_chain`은 기존 빔 클립 렌더링을 재사용한다.
- 생성한 다리·장비를 유지하면서 프레임마다 발 바닥 높이/부츠 중앙을 정렬한다.
  하단 사각 복사로 발을 고정하면 대기 무기 조각과 끊어진 무릎이 생겨 사용하지 않는다.
  새 45명의 `fixed_feet=false`는 실제 원점 정렬 방식이며 기존 5명의 고정 발은 보존한다.
  기존 attack 시간표/`hit_ms`, `anchor`, `scale`, `static.h`는 유지한다.
  무기 끝에 맞춘 새 `muzzle_at`은 원본 좌표와 함께 보존하고 부모가 로스터에 동기화했다.
- 50명 QC 모두 통과: 발 높이 최대 1px(허용2px), 잘림0px, 실제 알파·팔레트·해시 정상.
  실제 Godot 10페이지×1280×800/1000×625, 각 12프레임 배우와 14프레임 전투를 검수했다.
  자료는 `build/all-hero-sprites/all_50_comparison.png`, `visual-pages.json`, 각 페이지의
  `showcase.png`, `playback.gif`, `attack_sequence.png`, `battle_04.png`, `battle_08.png`다.

# 2D Pixel Art 제작 지침 및 NVIDIA DGX Spark GB10 워크플로 검토

> 기준: 첨부된 탑다운 RPG 스타일의 깔끔한 2D 픽셀아트  
> 작성일: 2026-09-13

## 결론

DGX Spark GB10으로 첨부 이미지와 비슷한 수준의 2D 픽셀아트를 만드는 것은 현실적입니다. 공개 모델과 오픈소스 도구로 로컬 제작 파이프라인을 만들 수 있습니다.

다만 목표를 구분해야 합니다.

- **분위기가 맞는 그림 한 장**: AI 생성과 간단한 보정으로 가능
- **게임에 넣을 캐릭터·맵·방향·애니메이션 전체**: AI 생성 후 픽셀 규격 통일, 프레임 정렬, 수동 검수 필요

추천 방식은 **AI로 후보 생성 → 픽셀 규격으로 정리 → 게임 안에서 검수**입니다. 장비 성능보다 제작 규칙의 일관성이 최종 품질을 더 크게 좌우합니다.

---

## 1. 참고 이미지에서 유지할 핵심

| 항목 | 특징 | 제작 규칙 |
|---|---|---|
| 시점 | 위에서 비스듬히 내려다보는 RPG 시점 | `top-down three-quarter view`, `oblique overhead view` 사용 |
| 비율 | 머리가 강조되고 몸이 압축됨 | 약 3~4등신부터 시작 |
| 실루엣 | 작은 크기에서도 머리·팔·다리 구분 | 장식보다 외곽 형태를 먼저 확정 |
| 윤곽선 | 어두운 외곽선으로 캐릭터 분리 | 원본 기준 1px 외곽선 통일 |
| 명암 | 부드러운 그라데이션보다 색면 | 재질별 3~4단계 명암 |
| 색 | 자연색 배경, 인물은 더 밝고 뚜렷함 | 공통 팔레트와 밝기 차이 유지 |
| 지형 질감 | 잔디·돌에 반복 패턴 존재 | 무작위 점 대신 반복 가능한 텍스처 |
| 원근 | 멀리 갈수록 급격히 작아지지 않음 | 게임용 평행 투영에 가까운 시점 |

이 스타일의 깔끔함은 모든 질감을 지우는 데 있지 않습니다. 캐릭터의 의미 없는 점은 줄이고, 배경의 반복 질감은 남깁니다.

---

## 2. 픽셀처럼 보이는 AI 그림과 게임용 픽셀아트의 차이

AI는 눈 2픽셀, 윤곽선 1픽셀 같은 규칙으로 그림을 조립하지 않고 픽셀아트처럼 보이는 이미지를 만듭니다. 따라서 아래 항목을 후처리로 관리해야 합니다.

| 흔한 문제 | 게임에서의 결과 |
|---|---|
| 픽셀 블록 크기가 부위마다 다름 | 화풍이 섞여 보임 |
| 외곽에 중간색이 많음 | 가장자리가 흐림 |
| 비슷한 색이 과도하게 많음 | 지저분한 색 얼룩 |
| 프레임마다 작은 점이 바뀜 | 움직일 때 깜빡임 |
| 발 위치가 변함 | 걷는 동안 덜컥거림 |
| 무기·장식이 달라짐 | 같은 캐릭터처럼 안 보임 |
| 타일 경계가 안 맞음 | 맵에 사각 경계 노출 |

단순 축소만으로는 해결되지 않습니다. 격자, 색, 형태, 정렬을 별도 규칙으로 정리해야 합니다.

---

## 3. 초기 제작 규격 제안

아래 값은 참고 이미지의 원본 수치가 아니라 유사한 인상을 위한 시작점입니다.

| 항목 | 권장 시작값 |
|---|---|
| 기본 타일 | 32×32px |
| 캐릭터 캔버스 | 64×64px |
| 실제 캐릭터 높이 | 44~52px |
| 비율 | 약 3~4등신 |
| 외곽선 | 대체로 1px |
| 캐릭터 팔레트 | 투명색 제외 16~24색 |
| 재질별 명암 | 3~4단계 |
| 광원 | 화면 왼쪽 위 등 한 방향 고정 |
| 투명도 | 완전 투명 또는 완전 불투명 |
| 결과물 | PNG + 스프라이트 시트 정보 |
| 화면 확대 | 2×, 3×, 4× 정수 배율 |

### 작화 규칙

1. 검은 실루엣만 봐도 부위가 구분되게 만듭니다.
2. 한 픽셀짜리 점보다 의미 있는 색 덩어리로 형태를 만듭니다.
3. 대각선의 계단 간격을 일정하게 정리합니다.
4. 모든 캐릭터·사물의 광원 방향을 맞춥니다.
5. 디더링은 지형에 선택적으로 쓰고 캐릭터에는 절제합니다.
6. 800% 확대 화면이 아니라 실제 게임 크기에서 판단합니다.

---

## 4. DGX Spark GB10 적합성

DGX Spark는 GB10 Grace Blackwell, 128GB 통합 메모리, 273GB/s 대역폭을 제공합니다.

- **통합 메모리**: 큰 모델과 여러 구성요소를 한 시스템에 올리는 데 유리합니다.
- **속도**: 대형 데스크톱 GPU보다 항상 빠르다는 뜻은 아닙니다.
- **강점**: 로컬에서 큰 모델, 편집 모델, LoRA 학습 실험을 구성하기 좋습니다.

| 작업 | 판단 | 비고 |
|---|---|---|
| SDXL 픽셀아트 생성 | 충분히 가능 | LoRA와 후처리가 핵심 |
| Z-Image-Turbo 생성 | 적합 | NVIDIA Spark 공식 시작 경로 있음 |
| FLUX.2 klein 4B 생성·편집 | 적합 | 모델 변형별 설정 구분 필요 |
| Qwen-Image 생성·편집 | 가능 | 큰 메모리 활용 후보 |
| 팔레트 정리·시트 조립 | 매우 적합 | GPU보다 제작 규칙이 중요 |
| 자체 스타일 LoRA 학습 | 가능 | 도구별 Arm64 호환성 확인 |
| 게임 전체 에셋 무검수 자동생산 | 비권장 | 일관성 검수가 병목 |

광고의 1 PFLOP은 특정 낮은 정밀도(FP4)의 지표입니다. 실제 속도는 모델·정밀도·해상도·워크플로에 따라 다릅니다.

참고: [NVIDIA DGX Spark 하드웨어](https://docs.nvidia.com/dgx/dgx-spark/hardware.html), [NVIDIA ComfyUI on DGX Spark](https://build.nvidia.com/spark/comfyui)

## 7. 후처리 절차

### 1) 후보 생성

모델과 LoRA가 잘 작동하는 512px 또는 1024px에서 후보를 만듭니다. 처음부터 64×64만 고집하면 형태가 무너질 수 있습니다.

### 2) 최종 픽셀 격자 맞춤

- 완성 픽셀아트 확대: 최근접 이웃 + 정수 배율
- 고해상도 후보 축소: 최근접 이웃만 고정하지 말고 결과 비교
- AI의 픽셀 블록 크기가 들쭉날쭉하면 격자·형태 수정을 병행

### 3) 공통 팔레트 적용

프레임마다 독립적으로 색을 추출하지 않습니다. 피부, 옷, 금속의 대표색과 명암색을 프로젝트 팔레트에 고정합니다.

### 4) 배경 제거와 윤곽 보정

초기 생성은 캐릭터와 겹치지 않는 단색 배경을 사용합니다. 이후 마스크로 제거하고 머리카락, 손, 무기 같은 가는 부분을 픽셀 편집기로 보정합니다.

### 5) 기준점과 캔버스 통일

모든 프레임을 같은 캔버스에 넣고 발 기준점을 정렬합니다. 걷기에서 의도적인 상하 움직임은 남깁니다.

### 6) 실제 화면 검수

눈, 손, 칼끝, 옷의 구분 같은 정보량 높은 픽셀을 우선 보정합니다.

---

## 8. 캐릭터·애니메이션 제작

초기 목표는 다음으로 제한하는 편이 좋습니다.

- 4방향 기준 이미지
- 방향별 걷기 4프레임
- 필요 시 대기 자세
- 무기·장식 위치 규칙
- 발 기준점과 프레임 시간

4방향 × 4프레임이면 캐릭터 한 명당 16프레임입니다. 공격·피격·사망 모션이 붙으면 관리량은 빠르게 증가합니다.

### 작업 순서

1. 기준 캐릭터 한 장을 완성합니다.
2. 같은 기준 이미지를 참조해 나머지 방향 후보를 만듭니다.
3. 머리·복장·무기 위치를 4방향에서 통일합니다.
4. 방향별 걷기 핵심 자세를 만듭니다.
5. 팔·다리·발 접지를 픽셀 단위로 정리합니다.
6. 실제 속도로 반복 재생하며 깜빡임과 미끄러짐을 확인합니다.

Seed를 고정해도 외형 일관성이 자동 보장되지는 않습니다. 확정한 기준 이미지와 수동 보정이 필요합니다.

---

## 9. 맵과 타일 제작

배경을 한 장의 이미지로 만들지 말고 조립 가능한 요소로 나눕니다.

| 요소 | 필요 구성 |
|---|---|
| 잔디 | 기본 타일과 변형 |
| 돌길 | 내부, 직선 경계, 바깥·안쪽 모서리 |
| 절벽 | 상단, 벽면, 하단, 모서리 |
| 키 큰 풀 | 지면과 분리된 전경 장식 |
| 나무·바위 | 개별 오브젝트와 충돌 정보 |
| 가림 처리 | 캐릭터보다 앞에 그려질 부분 |

타일은 최소 3×3으로 반복 배치해 경계와 반복 패턴을 확인합니다. `seamless`라는 프롬프트만으로 경계 타일 문제가 해결되지는 않습니다.

## 11. 설치·운영 원칙

DGX Spark는 Arm64 Linux 환경이므로 일반적인 x86 PC 설치 방법을 그대로 복사하지 않습니다.

1. NVIDIA Spark용 ComfyUI 공식 안내로 기본 생성부터 실행
2. 이미지 한 장이 정상 생성되는지 확인
3. 정상 동작한 모델·패키지 버전 기록
4. 픽셀 LoRA 하나만 추가
5. 후처리 단계 연결
6. 편집 모델과 추가 노드는 필요한 시점에 도입

Docker는 실행 환경을 묶는 도구일 뿐, x86 전용 프로그램을 Arm에서 자동 실행하게 만들지는 않습니다.

## 12. 에이전트 자동화

ComfyUI는 로컬 HTTP·WebSocket API를 제공합니다. 따라서 다음 작업을 자동화할 수 있습니다.

- 에셋 설명 목록 읽기
- 지정 모델·LoRA·Seed로 생성 요청

- 결과 파일 수집
- 크기·팔레트·투명도·기준점 검사
- 후보 비교 시트 생성
- 승인본만 게임 프로젝트로 내보내기

| 자동 검사 | 사람이 최종 판단 |
|---|---|
| 이미지 크기·형식 | 캐릭터의 매력 |

| 기준점 | 걷기 동작의 무게감 |

각 결과에는 모델·LoRA 버전, 프롬프트, Seed, 스텝, 참조 이미지, 후처리 규칙을 기록합니다.

## 13. 자체 스타일 LoRA

공개 LoRA만으로 캐릭터·지형의 일관성이 부족할 때 검토합니다. 시작 단계의 필수 작업은 아닙니다.

### 데이터 조건

- 사용 권한이 있는 원본 에셋
- 통일된 픽셀 크기와 확대 방식
- 같은 광원·윤곽선·팔레트
- 다양한 캐릭터·자세
- 내용과 방향을 설명한 캡션
- 학습 결과 비교용 검증 세트 분리

스타일 LoRA는 여러 인물을 같은 화풍으로 만드는 데 도움을 줍니다. 특정 캐릭터 외형 유지와 애니메이션 일관성은 별도 문제입니다.

NVIDIA는 DGX Spark에서 FLUX.1 Dreambooth LoRA를 학습하는 공식 예제를 제공합니다: [FLUX.1 LoRA 학습 예제](https://build.nvidia.com/spark/flux-finetuning)
